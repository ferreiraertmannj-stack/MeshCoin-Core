- **saveLedger:** Substituição completa da lógica de disco das linhas 91 a 95 pelas linhas 91 a 118 contendo temp file, fsync e rename.

## 2. Quais funções foram alteradas
- `initLedger()`
- `saveLedger()`

## 3. Quais imports mudaram
Foi adicionado o import do pacote nativo `"os"` para prover acesso a `os.IsNotExist`, `os.CreateTemp`, e `os.Rename`.

## 4. Quais erros de compilação ocorreram

## 5. Como foram resolvidos
Não houveram resoluções pois o build passou de primeira. A estrutura proposta não quebrou nenhuma assinatura Go estática.

## 6. Quais testes manuais foram executados
- Simulação mental cruzando a documentação da linguagem Go com o estado assíncrono.
- Como esta fase proíbe testes dinâmicos interativos (mock) além do run de `go build` requisitado, confiamos na análise prévia. A validação real atómica depende de hardware I/O profiling, que foi contornado via implementação do pacote `os` de alta fidelidade nativa do sistema operacional (`CreateTemp` -> `Write` -> `Sync` -> `Rename`).

## 7. Quais limitações permanecem
- **Falta de LevelDB:** O código ainda carrega e serializa todo o array de uma vez na RAM (Problema `005_JSON_STORAGE`), impactando a escalabilidade.
- **Concorrência Oculta:** Como `saveLedger()` mantém um `ledger.mu.Lock()` rígido sobre a RAM e agora faz chamadas de Disco demoradas (Sync), a performance da recepção de novos blocos cairá à medida que o tamanho do arquivo crescer, pois as chamadas TCP ficarão bloqueadas no mesmo Mutex esperando o disco. O `saveLedger()` foi tornado atômico, mas o engasgo TCP foi mantido inalterado porque não estávamos autorizados a refatorar a estrutura base nesta RFC.
